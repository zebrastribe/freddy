# Freddy Development Guidelines

## Project Overview

Freddy is a location tracking web application built with vanilla JavaScript, featuring modular architecture, Firebase integration, and progressive web app capabilities. This document outlines the development principles, architectural patterns, and best practices that should be followed when working on this project.

## 🏗️ Architectural Principles

### 1. Modular Design
- **Separation of Concerns**: Each module has a single, well-defined responsibility
- **Loose Coupling**: Modules communicate through well-defined interfaces
- **High Cohesion**: Related functionality is grouped together within modules

### 2. Feature-Based Organization
```
js/
├── lib/                    # Core utilities and configurations
│   ├── storage.js         # LocalStorage management
│   └── firebase_config.js # Firebase configuration
├── features/              # Feature-specific modules
│   ├── notifications/     # Push notification system
│   ├── checkin/          # Location check-in functionality
│   └── maps/             # Google Maps integration
└── modules/              # Third-party integrations
    ├── translation/       # i18n system
    └── recaptcha/        # reCAPTCHA integration
```

### 3. Class-Based Architecture
- Use ES6 classes for complex functionality
- Implement clear public APIs for each class
- Maintain private methods and properties where appropriate
- Follow the Single Responsibility Principle

## 📁 File Structure Standards

### Directory Organization
- **Root Level**: Only essential files (index.html, package.json, README.md)
- **js/**: All JavaScript source code
- **css/**: Stylesheets
- **img/**: Images and icons
- **docs/**: All documentation (except README.md)
- **tests/**: Test files and test pages
- **admin/**: Admin interface files

### Naming Conventions
- **Files**: Use snake_case for file names (e.g., `firebase_messaging.js`)
- **Classes**: Use PascalCase (e.g., `StorageManager`, `FirebaseMessaging`)
- **Methods**: Use camelCase (e.g., `getItem`, `requestPermission`)
- **Constants**: Use UPPER_SNAKE_CASE (e.g., `DEFAULT_LOCALE`)

## 🔧 Development Workflow

### 1. Feature Development Process
1. **Plan**: Define the feature scope and interfaces
2. **Create**: Implement in a dedicated feature module
3. **Test**: Create comprehensive test pages
4. **Integrate**: Update main app.js to use the new module
5. **Clean**: Remove old code and update documentation
6. **Commit**: Use descriptive commit messages

### 2. Module Creation Template
```javascript
class FeatureManager {
    constructor() {
        this.initialized = false;
        this.init();
    }

    init() {
        // Initialize the feature
        this.initialized = true;
    }

    // Public API methods
    publicMethod() {
        if (!this.initialized) {
            throw new Error('Feature not initialized');
        }
        // Implementation
    }

    // Private helper methods
    _privateMethod() {
        // Internal logic
    }
}

// Export for use in other modules
window.FeatureManager = FeatureManager;
```

### 3. Integration Pattern
```javascript
// In app.js
class App {
    constructor() {
        this.features = {};
        this.initFeatures();
    }

    initFeatures() {
        // Initialize feature managers
        this.features.storage = new StorageManager();
        this.features.messaging = new FirebaseMessaging();
        this.features.checkin = new CheckInManager();
        this.features.maps = new MapManager();
    }
}
```

## 🔒 Security and Best Practices

### 1. Configuration Management
- Store sensitive configuration in `js/config.js`
- Never commit API keys or secrets to version control
- Use environment-specific configuration when possible

### 2. Error Handling
- Implement comprehensive error handling in all modules
- Provide meaningful error messages
- Log errors appropriately for debugging

### 3. Input Validation
- Validate all user inputs
- Sanitize data before processing
- Use appropriate input types and constraints

## 📚 Documentation Standards

### 1. Code Documentation
- Use JSDoc comments for all public methods and classes
- **Each component/module file MUST begin with a JSDoc block describing:**
  - The component's purpose and responsibilities
  - Its requirements (e.g., browser APIs, external services)
  - Its dependencies (other modules, APIs, or services)
  - Its public API (methods, properties, events)
  - Usage examples
  - Error handling expectations
- Document complex algorithms and business logic
- Include usage examples for public APIs

### 2. README Updates
- Update README.md when adding new features
- Document new modules and their purposes
- Keep installation and setup instructions current

### 3. API Documentation
- Maintain `docs/API_REFERENCE.md` for all public APIs
- Document module interfaces and dependencies
- Include code examples and use cases

## 🚀 Performance Guidelines

### 1. Resource Loading
- Load scripts asynchronously when possible
- Minimize blocking operations
- Use appropriate loading strategies for different resource types

### 2. Memory Management
- Clean up event listeners when components are destroyed
- Avoid memory leaks in long-running applications
- Use appropriate data structures for performance

### 3. Caching Strategy
- Implement appropriate caching for frequently accessed data
- Use localStorage for user preferences and settings
- Cache API responses when appropriate

## 🔄 Refactoring Guidelines

### 1. When to Refactor
- Code duplication across modules
- Complex functions that do multiple things
- Tight coupling between modules
- Poor testability

### 2. Refactoring Process
1. **Identify**: Find code that needs refactoring
2. **Plan**: Design the new structure and interfaces
3. **Extract**: Create new modules with clear responsibilities
4. **Test**: Ensure all functionality works correctly
5. **Integrate**: Update main application to use new modules
6. **Clean**: Remove old code and update documentation

### 3. Migration Strategy
- Maintain backward compatibility during transitions
- Use feature flags for gradual rollouts
- Test thoroughly before removing old code

## 📋 Commit Message Guidelines

### Format
```
type(scope): description

[optional body]

[optional footer]
```

### Types
- **feat**: New feature
- **fix**: Bug fix
- **refactor**: Code refactoring
- **docs**: Documentation changes
- **test**: Test additions or changes
- **chore**: Maintenance tasks

### Examples
```
feat(notifications): add push notification toggle

refactor(storage): extract StorageManager class

fix(maps): resolve marker positioning issue
```
